GreenStep Challenge Admin

CISC 480 senior capstone · CS / technical · team project · SOAR + failure story

A full-stack web application that replaces the spreadsheets the Minnesota Pollution Control Agency had been using to administer its “GreenStep” sustainability challenges. Built with a four-person team for a real client, in production at greenstep.auriga.fyi.

Keywords: capstone, full-stack web development, React, Vite, Material UI, Supabase, PostgreSQL, Row-Level Security, Vercel, agile teamwork, real client engagement, sustainability, Minnesota Pollution Control Agency.

Situation

Our four-person team partnered with Kristin Mroz-Risse at the Minnesota Pollution Control Agency (MPCA) to replace the spreadsheets she had been using to run her agency's “GreenStep” sustainability challenges. Staff signed up to log everyday actions (biking to work, eliminating single-use plastics, shorter showers), and Kristin needed a tool to administer cohorts, define challenges and templates, track participation, and generate reports. The result is GreenStep Challenge Admin, a full-stack web application built in React + Vite + Material UI, backed by Supabase (PostgreSQL with Row-Level Security) and deployed on Vercel.

Obstacle

Building for a real client meant the requirements kept moving: Kristin would describe a workflow, we'd ship a slice, she'd see it and reshape the request. Internally, four developers working in parallel branches kept colliding. Auth changes shipped on one branch silently broke dev login on another. Schema refactors landed before the API code that needed them. The project's SQL migration files quietly drifted from what was actually deployed to the Supabase project.

Action (my personal contribution)

I owned the authentication stack and the schema, and I served as the de facto technical lead for production deploys. I migrated the team off magic-link auth (which corporate email scanners were pre-fetching and consuming) to an 8-digit OTP code flow, then layered Row-Level Security policies on top with a role hierarchy (SuperAdmin → Admin → GeneralUser) enforced at the database layer rather than the API. I refactored the front-end to lift duplicated ActionFormDialog and CategoryFormDialog components into a shared components/shared/forms/ module so the Challenge and Template forms stopped reaching across feature folders. For the project handoff to next semester's team, I squashed 14 partially-redundant migration files (including a four-migration RLS-flap loop) into two readable baseline files, reconciled them with the actually-deployed schema, and cleaned up the live supabase_migrations history table to match.

PRs I authored: #49 (4-color theme + auth race fix) · #70 (shared form components) · #82 (schema-mismatch fix for the Create Challenge bug) · #85 (migration squash for handoff).

Result

GreenStep ships to MPCA as a working admin tool replacing Kristin's spreadsheets, with role-based access enforced at the database level so the API cannot be bypassed from a browser console. Internally, the codebase is in a substantially more readable state for the next student team: two migration files instead of fourteen, shared form components in one place, and the presets/templates naming inconsistency documented.

1. What I was trying to do (context)

Fix a “Create Challenge” bug a teammate hit on the deployed app. The browser console reported Could not find the 'bgColorBody' column of 'challenges': a clear schema-mismatch error. I read the repository's 001_initial_schema.sql, saw the normalized layout it described (a separate themes table with a themeId foreign key), and shipped a fix that rewrote the form to send themeId and categoryId.

2. What didn't go as well as I hoped

The fix immediately failed in production with Could not find the table 'public.themes'. The migration files in the repo had been silently rewritten after being applied, and described a schema that was never actually deployed. I had built the wrong fix on top of fictional ground truth.

3. What I learned and what I do differently now

I now treat repo migration files as a claim about the schema, not the schema itself, especially in a multi-developer project where anyone can edit them. The right first step on any schema bug is to query the live database directly (supabase migration fetch, or pg_dump --schema-only) and diff that against the repo. I reverted the broken PR, wrote a single one-column migration that matched reality, and later went back to clean up the drifted migration files so the next team would never be misled the same way I was.
