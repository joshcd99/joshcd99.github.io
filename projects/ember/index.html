Ember

Personal finance & debt-payoff web application · CS / technical · solo project · SOAR

Ember is a personal-finance and debt-payoff web application I designed and built from scratch as a solo developer. It is a full-stack React/TypeScript app with a Supabase backend, deployed at ember.auriga.fyi. The point of view that distinguishes it from mainstream personal-finance tools is ADHD-centered design: momentum and visible progress over data density, celebration over shame, the next action over the dashboard.

Keywords: React, TypeScript, Vite, Supabase, PostgreSQL, Tailwind CSS, Recharts, Cloudflare Workers, Resend, progressive web app, debt payoff optimization, ADHD-centered design, human-computer interaction.

fig. 1 · Ember dashboard. Surfaces the single most impactful action of the day above the fold; debt-free countdown and monthly cash flow visible at a glance.

Situation

Managing personal debt is one of the most common sources of financial anxiety for young adults, yet most personal-finance tools are built for neurotypical users with stable incomes and strong executive function. I struggled to find software that matched the way I actually think about money: in terms of momentum, visible progress, and reduced cognitive load. So I decided to build my own.

Obstacle

The core challenge was twofold. Technically, I needed to build a full-stack web application from scratch as a solo developer while simultaneously finishing my CS degree and working full-time. The harder challenge was design: building something genuinely useful for ADHD users meant rethinking standard personal-finance UX from the ground up. Replace shame-based messaging with celebration mechanics, eliminate decision fatigue, and surface the single most impactful action at any given moment rather than overwhelming the user with data.

Action

I designed and built Ember as a React/TypeScript/Vite single-page application with a Supabase PostgreSQL backend, magic-link authentication, and a Cloudflare Workers middleware layer for integrations. The app implements multiple debt-payoff strategies (avalanche, snowball, custom drag-and-drop ordering), a scenario modeling engine with dual-axis projections showing debt and savings on a unified timeline, and a promotional / deferred-interest engine that calculates the true cost of missing a 0% APR deadline, including the silent interest that accumulates and dumps onto the balance at expiration.

I built the app progressively across several months, shipping features iteratively: household sharing, flexible bill recurrence rules, debt-type categorization with stacked area charts, a running cash-flow register, and PWA support for mobile installation. Throughout, I prioritized the ADHD use case: one-tap daily check-ins, streak tracking, forgiveness-first copy, and visceral payoff celebrations that make progress feel real.

Result

Ember is fully deployed on my personal domain, actively used for real debt management, and has validated several of its core design hypotheses in personal use. The deferred-interest engine correctly identified over $6,000 in potential interest savings on a single promotional balance, a number no mainstream finance app surfaces clearly. The project represents the most complete full-stack system I have built independently, integrating frontend engineering, database design, authentication, third-party API orchestration, and human-centered UX research into a single cohesive product.

Bonus failure story

An extra "failure → learning → change" arc on top of the main SOAR, included because the lesson is sharp and the math is fun.

What I was trying to do

Ship the deferred-interest engine: a calculator that surfaces the true cost of missing a 0% APR promotional deadline, so the user can see "if you don't pay this off by Mar 14, this much hidden interest dumps onto your balance."

What didn't go as well as I hoped

The first version produced a savings estimate of $3,817 on a debt where the correct figure was $6,278. The bug: the projection used interest_rate: 0 (the promotional rate) as the basis for projecting interest, instead of the post-promo rate that would actually apply if the deadline slipped. The app cheerfully under-reported the risk by ~40%, which is the exact opposite of what a financial decision-support tool should do.

What I learned and what I do differently now

I rebuilt the calculation engine around three explicit cases (active promo, expired promo, no promo), added a user-entered deferred-interest field, and added test cases keyed off the real-world numbers I'd verified by hand. The bigger lesson: when a tool is making a recommendation that money rides on, the calculation can't have an "obvious" path. Every branch needs to be named, every assumption explicit. I now treat any code that touches a number a user will make a decision on the same way I'd treat a database migration: assumptions are documented, edge cases are tests, and the math is checked against ground truth before shipping.
